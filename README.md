# GraphQL API Broken Access Control Leading to Buyer PII Exposure

## Overview

During security testing of a large social media utility platform, I identified a broken access control vulnerability in a GraphQL API endpoint that exposed buyer-related personally identifiable information (PII) to unauthorized seller accounts.

The application attempted to restrict access to certain customer analytics features to premium-tier sellers through frontend controls. However, the backend GraphQL API continued returning restricted customer metadata to free-tier seller accounts without enforcing proper authorization checks.

As a result, unauthorized sellers could access sensitive buyer-related information that was not intended to be visible to them through the standard user interface.

## Affected Component

The vulnerability affected a GraphQL endpoint responsible for returning customer-related analytics and metadata to seller dashboards.

Although the frontend application correctly hid certain analytics features from free-tier accounts, the backend API still returned restricted fields within GraphQL responses.

This created an authorization mismatch between the frontend application and backend API layer.

---

## Technical Summary

The GraphQL API returned customer-related objects containing metadata fields that should only have been accessible to premium-tier sellers.

Through direct API interaction, a low-privileged seller account could retrieve fields including:

* Buyer nearest city
* Buyer country
* Buyer device type information

The issue existed because authorization controls were implemented only at the presentation layer instead of being enforced server-side during GraphQL field resolution.

---

## Discovery Methodology

### 1. Application Traffic Analysis

Using an intercepting proxy and a GraphQL API client, I inspected requests generated by the seller dashboard and identified GraphQL queries responsible for retrieving customer information.

This revealed multiple nested response objects containing analytics and buyer-related metadata.

---

### 2. GraphQL Response Inspection

While reviewing API responses, I observed that several restricted fields were still returned even when authenticated as a free-tier seller account.

Although these values were hidden from the frontend interface, the backend API continued exposing them within raw GraphQL responses.

---

### 3. Authorization Validation

I confirmed that the exposed fields were consistently accessible using multiple low-privileged accounts.

The application failed to enforce authorization controls at the API layer, allowing unauthorized access to buyer metadata through direct query execution.

---

## Security Impact

This issue enabled unauthorized seller accounts to access buyer-related metadata that was intended only for premium-tier users.

Potential risks included:

* Geographic profiling of buyers
* Device fingerprinting
* Exposure of financial information
* Behavioral correlation of platform users
* Privacy violations affecting customer trust
* Unnecessary exposure of personal user information

Although testing was conducted using non-production buyer accounts containing placeholder information and using free products without requiring any payment methods, the vulnerability affected real application logic and authorization controls.

In a real-world scenario, legitimate buyer accounts could contain more fields like payment methods, amount payed, e.t.c.

As a result, the issue introduced a realistic risk of unauthorized exposure of personal user information to lower-privileged seller accounts.

The absence of financial information during testing was attributable to the use of test buyer profiles rather than the effectiveness of the authorization model itself.
.

---

## Root Cause Analysis

The vulnerability resulted from inconsistent authorization enforcement between the frontend application and backend GraphQL API.

### Frontend Behavior

The frontend correctly hid premium analytics features from free-tier accounts.

### Backend Behavior

The GraphQL resolver continued returning restricted fields regardless of account authorization level.

This created a scenario where security controls relied solely on frontend visibility restrictions rather than server-side access validation.

## Remediation Recommendations

Recommended mitigations included:

* Enforcing authorization checks at the GraphQL resolver level
* Implementing field-level access control
* Restricting sensitive response fields based on account permissions
* Returning only minimally required data
* Performing backend validation independently of frontend restrictions
* Conducting authorization testing across all API endpoints

## Key Takeaways

This assessment reinforced several important API security principles:

* Frontend restrictions should never be treated as authorization controls
* GraphQL APIs require strict field-level authorization validation
* Excessive data exposure can occur even when UI restrictions appear correct
* Sensitive metadata should always follow the principle of least privilege

The engagement also highlighted the importance of thoroughly inspecting API responses rather than relying solely on frontend application behavior.
